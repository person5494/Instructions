# SkillSwap — предложение по актуальной модели данных и логики.

## 1. Назначение документа

Этот документ фиксирует согласованную модель данных, хранение, Redux-состояние и ключевые пользовательские сценарии SkillSwap перед окончательной декомпозицией задач по логике приложения.

## 2. Границы текущего MVP

В текущую реализацию входят:

- каталог пользователей и навыков;
- поиск, фильтрация и сортировка;
- главная страница с секциями «Популярное», «Новое», «Рекомендуем»;
- отдельная страница навыка;
- регистрация в три шага и финальное подтверждение;
- локальная авторизация;
- один локально зарегистрированный пользователь на браузер;
- Favorites;
- предложения обмена;
- уведомления;
- редактирование личных данных;
- работа с локальными моковыми данными;
- сохранение изменяемого состояния в браузере;
- загрузочные, пустые и error-состояния;
- Redux Toolkit для глобального состояния.

Не входят:

- настоящий backend;
- реальные входящие заявки от других пользователей;
- изменение статусов заявок;
- отдельные полноценные разделы «Заявки» и «Мои обмены»;
- редактирование собственного предлагаемого навыка после завершения регистрации;
- несколько локальных аккаунтов в одном браузере;
- адаптив и тёмная тема;
- восстановление незавершённой регистрации после F5;
- дополнительное хеширование паролей;
- сжатие пользовательских изображений.

## 3. Базовое продуктовое правило

Один пользователь:

- предлагает ровно один навык, которому готов обучить;
- может хотеть научиться нескольким подкатегориям;
- имеет одну карточку в каталоге;
- не может завершить регистрацию без собственного предлагаемого навыка;
- не может создать второй предлагаемый навык.

Отдельная доменная сущность `Skill` с собственным `id` не требуется.

Предлагаемый навык существует только как часть `User`.

## 4. Сущность `User`

```ts
export type Gender = 'male' | 'female' | 'preferNotToSay'

export interface User {
  id: string
  name: string
  birthDate: string
  gender: Gender
  cityId: string
  avatarUrl: string | null
  description: string

  offeredSkill: OfferedSkill
  learningSubcategoryIds: string[]

  likesCount: number
  createdAt: string
}
```

### Назначение полей

- `id` — уникальный идентификатор пользователя.
- `name` — отображаемое имя.
- `birthDate` — дата рождения в ISO-формате.
- `gender` — выбранное значение пола.
- `cityId` — ID города из справочника.
- `avatarUrl` — изображение пользователя или `null`.
- `description` — необязательный раздел «О себе».
- `offeredSkill` — обязательный навык пользователя.
- `learningSubcategoryIds` — желаемые направления обучения.
- `likesCount` — базовое количество лайков карточки.
- `createdAt` — дата создания пользователя.

Возраст отдельно не хранится и вычисляется из `birthDate`.

## 5. Важное упрощение `learningSubcategoryIds`

Для локально зарегистрированного пользователя в `learningSubcategoryIds` физически хранится только базовая подкатегория, выбранная при регистрации.

Дополнительные подкатегории, появившиеся через Favorites, внутрь `User` не записываются.

Полный список «Хочу научиться» вычисляется selector'ом:

1. берётся базовая подкатегория пользователя;
2. добавляются `offeredSkill.subcategoryId` всех пользователей из Favorites;
3. дубликаты удаляются.

Это исключает ручное добавление и удаление подкатегорий при каждом изменении Favorites.

У моковых пользователей `learningSubcategoryIds` может содержать несколько значений прямо в `users.json`.

## 6. Вложенная структура `OfferedSkill`

```ts
export interface OfferedSkill {
  title: string
  categoryId: string
  subcategoryId: string
  description: string
  imageUrls: string[]
}
```

Правила:

- отдельного `id` нет;
- существует только внутри `User`;
- `imageUrls[0]` считается главным изображением;
- минимум 1 изображение;
- максимум 5 изображений.

## 7. Справочники

### Category

```ts
export interface Category {
  id: string
  name: string
  subcategories: Subcategory[]
}

export interface Subcategory {
  id: string
  name: string
}
```

Категории:

1. Бизнес и карьера.
2. Иностранные языки.
3. Дом и уют.
4. Творчество и искусство.
5. Образование и развитие.
6. Здоровье и лайфстайл.

Каждая подкатегория относится только к одной категории.

### City

```ts
export interface City {
  id: string
  name: string
}
```

Список городов статический, не менее 15 значений.

Категории, подкатегории и города:

- не хранятся в Redux;
- не дублируются в `localStorage`;
- импортируются как статические справочники.

## 8. Регистрация

Регистрация состоит из трёх шагов и финального подтверждения.

### Шаг 1

- email;
- пароль.

### Шаг 2

- имя;
- дата рождения;
- пол;
- город;
- одна подкатегория навыка, которому пользователь хочет научиться;
- аватар — необязательно.

### Шаг 3

- свободное название предлагаемого навыка;
- категория;
- подкатегория;
- описание;
- от 1 до 5 изображений.

### Финальное подтверждение

До подтверждения существует только `RegistrationDraft`.

После подтверждения одним действием создаются:

- `User`;
- `AuthAccount`;
- `AuthSession`.

После этого:

- пользователь считается зарегистрированным;
- добавляется в общий каталог;
- становится активным пользователем;
- `registration` slice очищается.

Кнопка «Редактировать» на экране «Ваше предложение» возвращает на шаг 3 с сохранённым черновиком.

## 9. `RegistrationDraft`

```ts
export interface RegistrationDraft {
  email: string
  password: string

  name: string
  birthDate: string
  gender: Gender | null
  cityId: string
  avatarUrl: string | null
  learningSubcategoryIds: string[]

  offeredSkill: OfferedSkill
}
```

`gender: null` используется только как незаполненное состояние формы.

Черновик:

- хранится только в Redux;
- не сохраняется в `localStorage`;
- не сохраняется в `sessionStorage`;
- после F5 регистрация начинается заново.

## 10. Обязательные поля регистрации

Обязательны:

- email;
- пароль;
- имя;
- дата рождения;
- пол;
- город;
- подкатегория желаемого навыка;
- название предлагаемого навыка;
- категория предлагаемого навыка;
- подкатегория предлагаемого навыка;
- описание предлагаемого навыка;
- минимум одно изображение предлагаемого навыка.

Необязательны:

- аватар;
- `User.description`.

## 11. Валидация

### Email

- обязательное поле;
- базовая проверка формата;
- должен быть уникален относительно текущего локального `AuthAccount`.

### Пароль

- минимум 8 символов;
- максимум 64 символа;
- минимум одна строчная буква;
- минимум одна заглавная буква;
- минимум одна цифра;
- минимум один спецсимвол.

Те же правила используются при смене пароля.

### Текстовые поля

Предварительные лимиты:

- `name`: 1–30 символов;
- `offeredSkill.title`: 1–30 символов;
- `offeredSkill.description`: 20–500 символов;
- `User.description`: 0–160 символов.

Перед валидацией и сохранением применяется `trim()`.

Повторяющиеся пробелы внутри текста не нормализуются.

### Дата рождения

- будущая дата запрещена;
- максимум 120 лет назад;
- минимальный возраст не ограничивается.

## 12. Изображения

### Ограничения

Аватар:

- максимум 1 изображение;
- необязателен.

Навык:

- минимум 1 изображение;
- максимум 5 изображений.

Для каждого файла:

- максимум 1 МБ;
- JPG/JPEG;
- PNG;
- WebP.

Изображения:

- не сжимаются;
- сохраняются как Data URL/Base64;
- пользовательские локальные изображения хранятся в `localStorage`;
- при ошибке переполнения хранилища показывается понятное локальное сообщение.

Если аватар отсутствует, используется стандартная заглушка.

Если файл слишком большой, неподдерживаемого формата или превышен лимит изображений — файл не добавляется и показывается локальная ошибка рядом с загрузчиком.

## 13. Галерея навыка

Используется уже подключённая библиотека.

Поведение:

- одно основное изображение;
- три миниатюры следующих изображений;
- последняя видимая миниатюра может показывать количество скрытых изображений;
- стрелки влево/вправо переключают изображения циклически;
- клик по миниатюре делает её основным изображением;
- при 1–3 изображениях отображаются только фактические изображения;
- пустые миниатюры не создаются;
- счётчик скрытых изображений не показывается, если скрытых изображений нет;
- при одном изображении стрелки скрываются;
- позиция галереи между открытиями страницы не сохраняется;
- главное изображение при открытии — `imageUrls[0]`;
- перестановка изображений пользователем не реализуется.

## 14. `User.description`

`description`:

- не заполняется при регистрации;
- после регистрации имеет `''`;
- является необязательным;
- редактируется только в профиле, в разделе «Личные данные»;
- если пустой, блок описания в интерфейсе не показывается.

## 15. Редактирование личных данных

После регистрации пользователь может менять:

- email;
- имя;
- дату рождения;
- пол;
- город;
- `description`;
- аватар;
- пароль.

При изменении email обновляется и `AuthAccount`.

Редактирование `offeredSkill` после завершения регистрации не реализуется.

Пункт «Мои навыки» не используется для редактирования, а ведёт на собственную страницу навыка.

## 16. Смена пароля

Текущий пароль не спрашивается.

Пользователь вводит:

- новый пароль;
- подтверждение нового пароля.

После проверки совпадения и валидации пароль обновляется в `AuthAccount`.

## 17. Один локальный пользователь на браузер

В одном браузере существует максимум один локально зарегистрированный пользователь.

Если пользователь проходит регистрацию повторно:

- старый `localUser` полностью заменяется;
- старый `AuthAccount` заменяется;
- старая активная сессия заменяется;
- Favorites очищаются;
- `SwapRequest` очищаются;
- уведомления очищаются;
- связанные локальные пользовательские данные очищаются.

Моковые пользователи из `users.json` при этом не меняются.

## 18. `AuthAccount`

```ts
export interface AuthAccount {
  userId: string
  email: string
  password: string
}
```

Особенности:

- существует максимум один локальный `AuthAccount`;
- хранится в `localStorage`;
- пароль хранится обычной строкой;
- это только учебная моковая авторизация;
- `createdAt` и `lastLoginAt` не хранятся;
- моковые пользователи `AuthAccount` не имеют.

Войти можно только под локально зарегистрированным пользователем.

## 19. `AuthSession`

```ts
export interface AuthSession {
  userId: string
}
```

Токен не используется.

Сессия:

- хранится в `localStorage`;
- переживает F5;
- переживает закрытие и повторное открытие браузера;
- удаляется при logout.

## 20. Защищённые маршруты

Защищены:

- `/profile`;
- `/favorites`;
- переход к собственной странице навыка `/skill/:currentUserId`.

Публичны:

- главная;
- каталог;
- чужие страницы навыков `/skill/:userId`.

Если неавторизованный пользователь открывает защищённый маршрут:

1. перенаправляется на `/login`;
2. исходный маршрут сохраняется;
3. после успешного входа пользователь возвращается на исходную страницу.

Если `/login` открыт напрямую, после входа можно вести на главную.

## 21. Страница навыка

Кнопка «Подробнее» ведёт на отдельную страницу:

```text
/skill/:userId
```

Отдельный `skillId` не нужен.

По `userId` получаем `User`, затем `offeredSkill`.

На странице:

- информация о пользователе;
- информация о предлагаемом навыке;
- галерея;
- действия Favorites и обмена;
- блок «Похожие предложения».

Пункт «Мои навыки» ведёт на:

```text
/skill/:currentUserId
```

## 22. Собственная страница навыка

На своей странице:

- кнопку Favorites скрываем;
- кнопку «Предложить обмен» скрываем;
- пользователь не может лайкнуть сам себя;
- пользователь не может отправить обмен самому себе.

## 23. Похожие предложения

Алгоритм:

1. исключить текущего пользователя;
2. сначала взять пользователей с той же `offeredSkill.subcategoryId`;
3. если карточек недостаточно — добрать пользователей с той же `offeredSkill.categoryId`, но другой подкатегорией;
4. максимум 8 карточек.

Одновременно показываются 4 карточки.

Стрелка вправо:

- переключает на следующую группу;
- после второй группы циклически возвращает к первой.

## 24. Favorites

`likedUserIds` внутри `User` не используется.

Favorites — отдельное пользовательское состояние.

```ts
favoriteUserIds: string[]
```

Правила:

- сохраняются в `localStorage`;
- переживают F5;
- переживают logout/login;
- новые Favorites показываются сверху;
- порядок сохраняется;
- собственную карточку добавить нельзя;
- карточка и страница навыка используют один и тот же источник состояния;
- на странице Favorites можно снять лайк прямо с карточки;
- отдельного поиска и фильтров на Favorites нет;
- если Favorites пуст, показывается сообщение «В избранном пока ничего нет».

## 25. Упрощённая логика `likesCount`

Отдельные `likesCount` overrides в `localStorage` не хранятся.

Для мокового пользователя актуальный `likesCount` вычисляется как:

```text
base likesCount из users.json
+
1, если пользователь находится в Favorites текущего localUser
```

Если пользователь удалён из Favorites, отображается исходный `likesCount` из моков.

У нового локального пользователя:

```ts
likesCount: 0
```

## 26. Полный список «Хочу научиться»

Для локального пользователя вычисляется selector'ом:

```text
базовая learningSubcategoryIds[0]
+
subcategoryId пользователей из Favorites
```

Повторы удаляются.

Количество элементов специально не ограничивается.

## 27. `SwapRequest`

Статус заявки пока не хранится.

```ts
export interface SwapRequest {
  id: string
  fromUserId: string
  toUserId: string
  createdAt: string
}
```

Сам факт существования заявки означает «Обмен предложен».

Правила:

- создаётся при нажатии «Предложить обмен»;
- максимум одна заявка на конкретный `toUserId`;
- повторную заявку тому же пользователю отправить нельзя;
- заявка не удаляется;
- отмена заявки не реализуется;
- пункты «Заявки» и «Мои обмены» остаются заглушками.

После создания заявки:

- показывается модальное окно «Вы предложили обмен»;
- пользователь остаётся на текущей странице;
- создаётся уведомление;
- кнопка меняется на неактивное состояние «Обмен предложен»;
- это состояние восстанавливается после F5 из сохранённых заявок.

## 28. `Notification`

Минимальная модель:

```ts
export interface Notification {
  requestId: string
  isRead: boolean
}
```

Отдельные `id`, `message`, `createdAt`, `type`, `userId` не используются.

Причины:

- `requestId` уже уникален;
- текст уведомления строится динамически из `SwapRequest` и `User`;
- дата берётся из `SwapRequest.createdAt`;
- тип уведомления пока один;
- локальный пользователь только один.

Если связанный `SwapRequest` отсутствует, уведомление считается некорректным и не показывается.

## 29. Уведомления в Header

Механика:

- новое уведомление создаётся с `isRead: false`;
- новые уведомления показываются в блоке «Новые уведомления»;
- просмотренные — в блоке «Просмотренные»;
- один массив делится по `isRead` при отображении;
- кнопка «Прочитать всё» переводит все уведомления в `isRead: true`;
- кнопка «Очистить» удаляет все просмотренные уведомления;
- сами `SwapRequest` при очистке уведомлений не удаляются;
- отдельное удаление одного уведомления не реализуется;
- уведомления не кликабельны;
- количество уведомлений не ограничивается.

Если новых уведомлений нет, секция «Новые уведомления» скрывается.

Если просмотренных нет, секция «Просмотренные» скрывается.

Если уведомлений нет вообще, показывается:

```text
Уведомлений нет
```

Меню не закрывается после «Прочитать всё» и «Очистить».

## 30. Индикатор уведомлений

Числового badge нет.

Если существует хотя бы одно `Notification` с `isRead: false`, возле колокольчика показывается оранжевый кружок.

Индикатор зависит только от наличия непрочитанных уведомлений и не зависит от того, открыто меню или нет.

После «Прочитать всё» индикатор исчезает.

## 31. Главная страница — «Популярное»

Алгоритм:

- сортировка пользователей по актуальному `likesCount` по убыванию;
- максимум 9 карточек;
- сначала показываются 3;
- по кнопке раскрываются до 9;
- после раскрытия кнопка меняется на «Свернуть»;
- можно вернуть отображение к 3 карточкам.

## 32. Главная страница — «Новое»

Алгоритм:

- сортировка по `createdAt` от новых к старым;
- максимум 9 карточек;
- сначала показываются 3;
- можно раскрыть до 9;
- можно свернуть обратно до 3.

Для локального пользователя `createdAt` ставится в момент финального подтверждения регистрации.

## 33. Главная страница — «Рекомендуем»

Алгоритм:

- пользователи случайно перемешиваются один раз при открытии главной страницы;
- порядок сохраняется в локальном состоянии секции;
- карточки не перемешиваются на каждом render;
- повторы уже показанных карточек запрещены;
- первая порция — 6 карточек;
- следующие порции — по 6;
- загрузка продолжается до исчерпания списка.

Отдельной кнопки нет.

Догрузка:

- через `IntersectionObserver`;
- внизу секции находится sentinel;
- при попадании sentinel во viewport запускается искусственная задержка;
- во время задержки показывается `Spinner`;
- затем добавляется следующая порция;
- когда данные заканчиваются, observer больше не запускает загрузку.

Состояние «Рекомендуем» не хранится в Redux и не сохраняется после F5.

## 34. Поиск

Поиск работает только по:

```ts
offeredSkill.title
```

Не используется поиск по:

- имени пользователя;
- категории;
- подкатегории;
- описаниям.

Поведение:

- регистронезависимый;
- частичное совпадение через `includes`;
- поисковая строка хранится локально на странице каталога;
- не сохраняется после F5;
- работает одновременно с фильтрами.

## 35. Фильтры каталога

### Режим

RadioButton:

- «Все»;
- «Хочу научиться»;
- «Могу научить».

Логика:

- «Все» — выбранная подкатегория проверяется и в `offeredSkill.subcategoryId`, и в полном вычисляемом списке желаемых подкатегорий;
- «Хочу научиться» — только по желаемым подкатегориям;
- «Могу научить» — только по `offeredSkill.subcategoryId`.

### Навыки

- категории раскрываются;
- внутри — подкатегории с checkbox;
- клик по checkbox категории выбирает все подкатегории;
- повторный клик снимает все;
- частичный выбор переводит checkbox категории в `indeterminate`;
- ручной выбор всех подкатегорий переводит категорию в полностью выбранное состояние;
- снятие одной подкатегории переводит категорию из полного состояния в `indeterminate`;
- клик по названию категории только раскрывает или сворачивает список;
- стрелка рядом выполняет то же действие.

### Пол автора

RadioButton:

- «Не имеет значения»;
- «Мужской»;
- «Женский».

`preferNotToSay`:

- попадает только в «Не имеет значения»;
- не попадает в мужскую или женскую выдачу.

### Город

- популярные крупные города видны сразу;
- остальные находятся в раскрывающемся списке;
- выбор через checkbox;
- можно выбрать несколько.

### Правила сочетания

- внутри одной группы — `OR`;
- между разными группами — `AND`.

## 36. Сортировка каталога

Обязательный вариант:

- «Сначала новые»;
- сортировка по `createdAt` по убыванию.

Опционально можно добавить переключение на:

- «По популярности»;
- сортировка по актуальному `likesCount` по убыванию.

Сортировка применяется уже после фильтрации.

## 37. Пустая выдача каталога

Если ничего не найдено:

```text
Ничего не найдено
```

Можно добавить короткую подсказку попробовать сбросить фильтры.

Отдельная кнопка в пустом состоянии не нужна, поскольку кнопка «Сбросить» уже есть в фильтрах.

## 38. Сохранение фильтров

Фильтры и сортировка хранятся в `sessionStorage`.

Это означает:

- F5 в той же вкладке сохраняет состояние;
- закрытие вкладки очищает состояние;
- новая вкладка начинает с исходных фильтров;
- поисковая строка не сохраняется.

При logout:

- фильтры очищаются;
- сортировка очищается;
- данные удаляются из `sessionStorage`.

Кнопка «Сбросить»:

- сбрасывает все фильтры;
- сбрасывает сортировку;
- очищает поисковую строку;
- удаляет сохранённые значения из `sessionStorage`.

## 39. Источник пользователей

Моковые пользователи:

```text
users.json
```

Локальный пользователь:

```text
localStorage
```

В `users` slice они хранятся раздельно:

```ts
interface UsersState {
  mockUsers: User[]
  localUser: User | null
  status: 'idle' | 'loading' | 'success' | 'error'
  error: string | null
}
```

`isRefreshing` не используется.

`selectAllUsers` возвращает:

```text
mockUsers + localUser, если он существует
```

## 40. Загрузка `users.json`

Используется асинхронная загрузка через `createAsyncThunk`.

Состояния:

- `idle`;
- `loading`;
- `success`;
- `error`.

Во время первой загрузки показывается `Spinner`.

При ошибке:

- показывается error-state;
- есть возможность повторить загрузку.

При повторной попытке уже загруженные пользователи не очищаются.

Отдельного фонового refresh-механизма нет.

## 41. Redux slices

### `users`

Хранит:

- `mockUsers`;
- `localUser`;
- статус загрузки;
- ошибку загрузки.

### `auth`

Хранит:

- `userId` активной сессии;
- состояние авторизации.

Полный `User` здесь не дублируется.

Текущий пользователь получается selector'ом из `users`.

### `registration`

Хранит `RegistrationDraft` между тремя страницами регистрации.

### `favorites`

Хранит:

```ts
favoriteUserIds: string[]
```

### `requests`

Хранит:

```ts
SwapRequest[]
```

### `notifications`

Хранит:

```ts
Notification[]
```

Actions как минимум:

- `markAllAsRead`;
- `clearReadNotifications`.

### `catalogFilters`

Хранит:

- режим фильтра;
- выбранные подкатегории;
- выбранный пол;
- выбранные города;
- сортировку.

Поисковая строка сюда не входит.

## 42. Что остаётся локальным UI-state

Не кладём в Redux:

- поисковую строку;
- раскрытие категорий в фильтрах;
- открытие и закрытие модалок;
- состояние галереи;
- случайный порядок «Рекомендуем»;
- количество уже загруженных карточек «Рекомендуем».

## 43. Selectors

Нужны как минимум:

```ts
selectAllUsers
selectCurrentUser
selectUserById
selectPopularUsers
selectNewUsers
selectSimilarUsers
selectCatalogUsers
selectEffectiveLearningSubcategoryIds
selectEffectiveLikesCount
```

### `selectCatalogUsers`

- получает общий список пользователей;
- применяет фильтры;
- затем применяет сортировку;
- возвращает готовый список.

Поиск накладывается на результат уже локально на странице каталога через `useMemo`.

### `selectSimilarUsers`

По `userId`:

1. исключает текущего пользователя;
2. ищет ту же подкатегорию;
3. затем ту же категорию;
4. ограничивает до 8 карточек.

## 44. `storageService`

Используется один простой общий сервис.

Не создаются отдельные:

- `authStorage`;
- `usersStorage`;
- `favoritesStorage`;
- `requestsStorage`;
- `notificationsStorage`.

Минимальная ответственность сервиса:

```ts
get<T>()
set<T>()
remove()
```

Для `localStorage` и `sessionStorage`.

Сложные repository/adapter-слои не нужны.

## 45. Browser storage

### `localStorage`

Хранятся:

- `localUser`;
- `AuthAccount`;
- `AuthSession`;
- Favorites;
- `SwapRequest[]`;
- `Notification[]`;
- пользовательские изображения в составе локальных данных.

### `sessionStorage`

Хранятся:

- фильтры каталога;
- сортировка каталога.

Не хранятся:

- поисковая строка;
- `RegistrationDraft`;
- UI-состояния.

## 46. Восстановление состояния

Сохранённые данные восстанавливаются через `storageService` при инициализации соответствующих состояний.

Компоненты напрямую с `localStorage` или `sessionStorage` не работают.

## 47. Logout

При logout:

Удаляется:

- `AuthSession`;
- состояние текущей авторизации в Redux;
- Favorites из активного Redux-state;
- requests из активного Redux-state;
- notifications из активного Redux-state;
- filters/sort из `sessionStorage`;
- `RegistrationDraft`.

Не удаляется из `localStorage`:

- `localUser`;
- `AuthAccount`;
- Favorites;
- `SwapRequest[]`;
- `Notification[]`.

Они восстанавливаются после следующего login того же локального пользователя.

`users` slice при logout не очищается, потому что каталог публичный.

## 48. Повторная регистрация

Повторная регистрация в том же браузере полностью заменяет предыдущего локального пользователя.

При финальном подтверждении новой регистрации очищаются данные старого локального пользователя:

- `localUser`;
- `AuthAccount`;
- `AuthSession`;
- Favorites;
- requests;
- notifications.

После этого сохраняются данные нового пользователя.

## 49. Генерация ID

Для:

- `User.id`;
- `SwapRequest.id`

используется:

```ts
crypto.randomUUID()
```

Отдельный ID для `Notification` не нужен.

## 50. Принцип архитектуры

Основная цель текущей реализации — не воспроизводить production-backend, а показать работающий учебный MVP с понятной логикой и минимальным количеством дублирующего состояния.

Поэтому:

- не хранить данные, которые можно надёжно вычислить;
- не дублировать одни и те же значения в нескольких сущностях;
- не создавать Redux slice для чисто визуального состояния;
- не использовать thunk для синхронных операций без необходимости;
- не строить лишние storage/repository abstraction layers;
- не реализовывать жизненный цикл заявок, которого нет в интерфейсе;
- не усложнять моковую авторизацию механизмами реальной безопасности, которых без backend всё равно нет.

## 51. Что можно скорректировать позже без изменения архитектуры

К этой категории относятся:

- точные лимиты длины текстовых полей;
- конкретный список городов;
- точные тексты empty/error-состояний;
- длительность искусственной задержки в «Рекомендуем»;
- наличие опциональной сортировки «По популярности»;
- визуальные детали галереи;
- финальные названия storage-ключей;
- конкретные названия Redux actions/selectors.

Эти решения не должны блокировать декомпозицию основной логики.
